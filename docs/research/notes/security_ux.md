# TOTP/HOTP in a password manager: security and UX requirements for the "Miftawerk OTP" KeePass 2 plugin

Research date: 2026-10-23. Legend: **[V]** = verified against the primary source (and, for test vectors, also re-computed locally with Python `hmac`/`hashlib`); **[S]** = secondary/community source; **[I]** = inference by the researcher, not stated by a source.

## 1. RFC 4226 (HOTP) / RFC 6238 (TOTP): algorithm, dynamic truncation, official test vectors, errata

### Takeaway
The algorithm is small and fully specified; the official vectors (RFC 4226 App. D, RFC 6238 App. B) are directly usable as unit tests, **but** the RFC 6238 SHA-256/SHA-512 vectors only reproduce with 32-byte and 64-byte seeds (verified Erratum 2866), not with the 20-byte ASCII secret the appendix text implies. This is a classic trap that should be encoded as a test.

### Cited Findings
- [V] HOTP = Truncate(HMAC-SHA-1(K, C)) mod 10^Digit. Dynamic truncation: offset = low 4 bits of the last HMAC byte; take 4 bytes from that offset; mask the top bit (`& 0x7f`) "to avoid signed/unsigned ambiguity"; the 31-bit result mod 10^Digit. Section 5.4 worked example: offset 0xa, DBC 0x50ef7f19, HOTP 872921 — [RFC 4226 §5.3–5.4](https://www.rfc-editor.org/rfc/rfc4226)
- [V] "MUST extract a 6-digit code at a minimum and possibly 7 and 8-digit code" — [RFC 4226 §5.3](https://www.rfc-editor.org/rfc/rfc4226)
- [V] Shared secret: "MUST be at least 128 bits"; "RECOMMENDs a shared secret length of 160 bits" (R6) — [RFC 4226 §4](https://www.rfc-editor.org/rfc/rfc4226)
- [V] Modulo bias of 31-bit value mod 10^6 is small (values 0–483647 prob. ≈1.00024045/10^6 vs ≈0.99977478/10^6 otherwise); RFC calls it negligible — [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226)
- [V] Server-side: throttling parameter (§7.3) and a bounded look-ahead window s for HOTP resync (§7.4) — [RFC 4226 §7](https://www.rfc-editor.org/rfc/rfc4226)
- [V] **RFC 4226 Appendix D** (secret ASCII `12345678901234567890` = hex `3132333435363738393031323334353637383930`, 6 digits, SHA-1), counter 0–9: `755224, 287082, 359152, 969429, 338314, 254676, 287922, 162583, 399871, 520489`. Intermediate truncated values also given, e.g. count 0: HMAC `cc93cf18508d94934c64b65d8ba7667fb7cde4b0`, truncated `0x4c93cf18` = 1284755224 — [RFC 4226 App. D](https://www.rfc-editor.org/rfc/rfc4226). Re-computed locally: all 10 match.
- [V] TOTP: T = floor((UnixTime − T0) / X), T0 = 0, X = 30 s default; implementations must handle T beyond 32 bits (post-2038); T is fed as an 8-byte big-endian counter into HOTP — [RFC 6238 §4](https://www.rfc-editor.org/rfc/rfc6238); 64-bit big-endian clarification proposed in [Erratum 8672 (Reported)](https://errata.rfc-editor.org/rfc6238)
- [V] "TOTP implementations MAY use HMAC-SHA-256 or HMAC-SHA-512" (SHA-1 is the HOTP base) — [RFC 6238 §1.2](https://www.rfc-editor.org/rfc/rfc6238)
- [V] "Keys SHOULD be of the length of the HMAC output to facilitate interoperability" — [RFC 6238 §5.1](https://www.rfc-editor.org/rfc/rfc6238)
- [V] **RFC 6238 Appendix B** (X=30, T0=0, 8 digits):

  | Unix time | UTC | T (hex) | SHA1 | SHA256 | SHA512 |
  |---|---|---|---|---|---|
  | 59 | 1970-01-01 00:00:59 | 0000000000000001 | 94287082 | 46119246 | 90693936 |
  | 1111111109 | 2005-03-18 01:58:29 | 00000000023523EC | 07081804 | 68084774 | 25091201 |
  | 1111111111 | 2005-03-18 01:58:31 | 00000000023523ED | 14050471 | 67062674 | 99943326 |
  | 1234567890 | 2009-02-13 23:31:30 | 000000000273EF07 | 89005924 | 91819424 | 93441116 |
  | 2000000000 | 2033-05-18 03:33:20 | 0000000003F940AA | 69279037 | 90698825 | 38618901 |
  | 20000000000 | 2603-10-11 11:33:20 | 0000000027BC86AA | 65353130 | 77737706 | 47863826 |

  — [RFC 6238 App. B](https://www.rfc-editor.org/rfc/rfc6238). Re-computed locally: all 18 match **with the per-algorithm seeds below**.
- [V] Seeds from the RFC's Java reference code: SHA1 `3132333435363738393031323334353637383930` (20 B); SHA256 `3132333435363738393031323334353637383930313233343536373839303132` (32 B = "12345678901234567890" + "123456789012"); SHA512 = "12345678901234567890" ×3 + "1234" (64 B) — [RFC 6238 App. A](https://www.rfc-editor.org/rfc/rfc6238)
- [V] **Erratum 2866 (Technical, Verified)**: Appendix B wrongly implies one shared secret; SHA-256 needs the 32-byte and SHA-512 the 64-byte seed. **Erratum 5132 (Reported)** makes the same point from the reference code. Other errata: 4678 (Verified, Javadoc `truncationDigits` → `DIGITS_POWER`), 4530 (Reported, recursive overload), 7271 (Reported, digit formatting not constant-time), 8672 (Reported, 64-bit T clarification), 4249 (Reported, RFC 6030 lacks TOTP suite strings), plus editorial 4881/3338/3339 — [RFC 6238 errata](https://errata.rfc-editor.org/rfc6238)
- [V, local computation] Negative control: using the 20-byte seed with SHA-256 / SHA-512 at T=59 yields `32247374` / `69342147` (not the published `46119246` / `90693936`). An implementation that "fails" the SHA-256/512 vectors this way has the seed wrong, not the algorithm.
- [V] RFC reference code is under Simplified BSD; copying it requires carrying that licence text — [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) (relevant because the plugin is MIT and "built from scratch").

### Inferences
- [I] Testable requirements: (R1) HOTP counters 0–9 reproduce App. D; (R2) all 18 App. B values reproduce with per-algorithm seeds; (R3) T=20000000000/30 (> 2^32 seconds input) works, i.e. 64-bit counter; (R4) leading zeros preserved (`07081804`) — output must be a zero-padded string, never an int; (R5) offset computed from the *last* byte of the HMAC regardless of hash length (20/32/64 B).
- [I] Writing the algorithm from the RFC text (not copying the Java appendix) keeps the MIT licence clean.

### Gaps
- No errata were checked for RFC 4226 itself (only RFC 6238's errata page was fetched).

## 2. Parameters in the wild; drift; ±1 window; remaining seconds; NTP vs system time

### Takeaway
SHA-1 / 6 digits / 30 s is the de-facto default everywhere; 7/8 digits, 60 s and SHA-256/512 exist but some major authenticators historically ignored those URI parameters. The single largest real-world failure cause is the local clock being off, so the UI must make time visible and diagnosable. NTP queries are unauthenticated plain UDP and leak some fingerprintable data, so any built-in time check should be opt-in.

### Cited Findings
- [V] Google Key URI format: "the algorithm parameter is ignored by the Google Authenticator implementations"; "the period parameter is ignored"; digits ignored on Android/BlackBerry; secret is Base32 (RFC 3548) and "padding … should be omitted"; issuer prefix and account separated by literal or URL-encoded colon, and "Neither issuer nor account name may themselves contain a colon"; `counter` required for HOTP — [google-authenticator wiki: Key Uri Format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format)
- [V] KeePass 2.x native OTP: `TimeOtp-Length` default 6, **max 8**; `TimeOtp-Period` default 30; `TimeOtp-Algorithm` default HMAC-SHA-1, also HMAC-SHA-256/512; "The date and the time of your system must be correct" — [KeePass Placeholders help](https://keepass.info/help/base/placeholders.html)
- [V] Bitwarden: defaults SHA-1/6 digits/30 s; supports sha1/sha256/sha512, digits 1–10, period > 0, Steam via `steam://` (5-char alphanumeric); example `otpauth://totp/Test:me?secret=JBSWY3DPEHPK3PXP&algorithm=sha256&digits=8&period=60` — [Bitwarden Integrated Authenticator](https://bitwarden.com/help/integrated-authenticator/)
- [V] Proton Pass describes codes as six digits changing every 30 seconds — [Proton support: pass-2fa](https://proton.me/support/pass-2fa)
- [V] KeePassXC docs: codes "typically six digits long and change every 30 seconds"; "Your computer time must be synchronized with an internet time source to generate valid TOTP codes" — [KeePassXC docs source, DatabaseOperations.adoc](https://raw.githubusercontent.com/keepassxreboot/keepassxc/develop/docs/topics/DatabaseOperations.adoc)
- [V] RFC 6238: verifier should allow "at most one time step" for network delay; window size is a security/usability trade-off; RFC example drift tolerance two steps back; verifier must reject replay of an already-accepted OTP — [RFC 6238 §5.2, §6](https://www.rfc-editor.org/rfc/rfc6238). (These are verifier-side; the generator side only needs a correct clock.)
- [S] KeePassXC maintainer on wrong-code reports: "The single most prevalent error with TOTP (99.9%) is system time being off" — [keepassxc#8300](https://github.com/keepassxreboot/keepassxc/issues/8300); standard reply "Sync your computer time" in [#12860](https://github.com/keepassxreboot/keepassxc/issues/12860), [#10799](https://github.com/keepassxreboot/keepassxc/issues/10799), [#10807](https://github.com/keepassxreboot/keepassxc/issues/10807) (user confirmed clock was set manually / ≥30 s off), [#6646](https://github.com/keepassxreboot/keepassxc/issues/6646), [#11320](https://github.com/keepassxreboot/keepassxc/issues/11320), [#4377](https://github.com/keepassxreboot/keepassxc/issues/4377); [#12135](https://github.com/keepassxreboot/keepassxc/issues/12135) reporter: clock "about 50 sec behind… NTP-Setting is there but didn't work".
- [S] Time-zone/DST edge cases: `TZ` env var breaks codes (open, [#10802](https://github.com/keepassxreboot/keepassxc/issues/10802)); wrong codes after DST/time-zone switch until restart ([#9975](https://github.com/keepassxreboot/keepassxc/issues/9975), [#4511](https://github.com/keepassxreboot/keepassxc/issues/4511)).
- [S] Users ask for: per-entry time offset ([#11753](https://github.com/keepassxreboot/keepassxc/issues/11753)), custom offset or NTP ([#12409](https://github.com/keepassxreboot/keepassxc/issues/12409)), remote-server time ([#3498](https://github.com/keepassxreboot/keepassxc/issues/3498)), docs mentioning wrong clock ([#12710](https://github.com/keepassxreboot/keepassxc/issues/12710)), time-left in preview ([#4461](https://github.com/keepassxreboot/keepassxc/issues/4461)), showing the next code during the last 5 s ([#11340](https://github.com/keepassxreboot/keepassxc/issues/11340)), several codes around now ([#5661](https://github.com/keepassxreboot/keepassxc/issues/5661)), progress bar regression in 2.8.0 (opened 2026-10-22, [#13825](https://github.com/keepassxreboot/keepassxc/issues/13825)).
- [V] NTP privacy: per the IETF NTP data-minimization draft, accurate values in client request fields let "a passive observer … fingerprint clients and track them as they move across networks"; origin/receive timestamps are "a particularly severe information leak"; without crypto auth, origin-timestamp checks are clients' "primary defense against blind spoofing" — [draft-ietf-ntp-data-minimization](https://datatracker.ietf.org/doc/html/draft-ietf-ntp-data-minimization)

### Inferences
- [I] Compute T from UTC epoch (`DateTimeOffset.UtcNow.ToUnixTimeSeconds()` in .NET) and never from local time; this makes TZ/DST bugs structurally impossible (they were all local-time-related in KeePassXC).
- [I] Display: code grouped (e.g. "123 456") but copied/typed **without** the space (KeePassXC users complained, [#12039](https://github.com/keepassxreboot/keepassxc/issues/12039)); remaining seconds = period − (unix mod period); optionally show next code when ≤ 5 s remain.
- [I] Make clock problems diagnosable instead of silently fetching network time: e.g. an opt-in "check clock" action that does one NTP/NTS query and reports the offset, with a privacy note; default = system time, no network traffic. A per-entry/time offset setting is a frequently requested escape hatch.
- [I] A "±1 window" display (previous/current/next) is generator-side UX; servers usually accept ±1 step already (RFC recommendation), so showing previous/next mainly helps at boundaries.

### Gaps
- No authoritative, quantified survey of which services use SHA-256/512, 7/8 digits or 60 s was found; only vendor support matrices. Treat "SHA-1/6/30 dominates" as widely documented default, not a measured statistic.
- RFC 8915 (NTS) text was not fetched; whether NTS removes the fingerprinting issue is unverified here.
- Whether current Google Authenticator versions still ignore `algorithm`/`period` is unverified (wiki page is archived/old).

## 3. Secret handling inside KeePass 2: memory protection, logs/temp files, clipboard, auto-type

### Takeaway
KeePass gives a plugin the building blocks (in-memory encrypted protected strings, clipboard exclusion formats, auto-clear) but its own docs admit plaintext copies appear during display, clipboard transfer and placeholder replacement. A plugin must store the secret as a protected field and avoid creating additional plaintext copies (logs, exceptions, temp files, QR images, clipboard history).

### Cited Findings
- [V] "While KeePass is running, sensitive data is stored encryptedly in the process memory"; scope limited (master key, entry passwords; user names, notes, attachments not covered "For performance reasons"); DPAPI key in non-swappable memory; fallback ChaCha20 with random key ("less secure than DPAPI"); ChaCha20 on Mono — [KeePass Security help](https://keepass.info/help/base/security.html)
- [V] Plaintext exposure: displaying data in standard controls, clipboard transfers, placeholder replacement and search create unencrypted copies; "Windows and .NET may make copies of the data (in the process memory) that cannot be erased by KeePass" — [KeePass Security help](https://keepass.info/help/base/security.html)
- [V] KeePass native OTP stores parameters "as entry strings" (`TimeOtp-Secret[-Hex|-Base32|-Base64]`, `HmacOtp-Secret…`, `HmacOtp-Counter` auto-incremented on each replacement); placeholders `{TIMEOTP}`, `{HMACOTP}` — [KeePass Placeholders help](https://keepass.info/help/base/placeholders.html)
- [V] Windows clipboard history / Cloud Clipboard exclusion: `ExcludeClipboardContentFromMonitorProcessing` (any data → excluded from history and sync), `CanIncludeInClipboardHistory` (DWORD 0 → not in history), `CanUploadToCloudClipboard` (DWORD 0 → not synced); obtain IDs via `RegisterClipboardFormat` — [Microsoft Learn: Clipboard Formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats)
- [V] KeePass 2.44: with option "Do not store data in the Windows clipboard history and the cloud clipboard" on "(which it is by default)", KeePass "additionally excludes its clipboard contents from processing by Windows' internal ClipboardMonitor component"; "Clipboard Viewer Ignore" format now on by default — [KeePass 2.44 release notes](https://keepass.info/news/n200120_2.44.html). CF_CLIPBOARD_VIEWER_IGNORE first added in 2.03 alpha ([news](https://keepass.info/news/n071011_2.03_alpha.html)); opt-out added in 2.08 (per search summary of the changelog, [S]).
- [S] Third-party clipboard managers (CopyQ docs) list the same formats and state they are used by Windows Credential Manager and most password managers — [CopyQ security docs](https://copyq-de.readthedocs.io/de/stable/security.html)
- [V] Real incident, secrets in logs: Proton Authenticator for iOS wrote full TOTP secrets in plaintext into its debug logs (Settings > Logs); found when a user prepared a bug report; fixed in 1.1.1 (Aug 2025) — [BleepingComputer](https://www.bleepingcomputer.com/news/security/proton-fixes-authenticator-bug-leaking-totp-secrets-in-logs/)
- [V] Proton Pass on Android auto-copies the TOTP to the clipboard after login — [Proton support](https://proton.me/support/pass-2fa); Bitwarden extension auto-copies TOTP after autofill by default, with a "Clear clipboard" dropdown — [Bitwarden](https://bitwarden.com/help/integrated-authenticator/)
- [S] KeePassXC auto-type edge cases: stale `{TOTP}` after `{DELAY}` ([#12682](https://github.com/keepassxreboot/keepassxc/issues/12682)), brackets in password break `{TOTP}` ([#11500](https://github.com/keepassxreboot/keepassxc/issues/11500)), wrong TOTP when multiple auto-type ([#2210](https://github.com/keepassxreboot/keepassxc/issues/2210)), `{TOTP}` vs KeePass `{TIMEOTP}` naming ([#9316](https://github.com/keepassxreboot/keepassxc/issues/9316)).
- [S] KeePassXC: TOTP display window kept the database from auto-locking / stayed open after lock — [#923](https://github.com/keepassxreboot/keepassxc/issues/923), [#2407](https://github.com/keepassxreboot/keepassxc/issues/2407), [#2447](https://github.com/keepassxreboot/keepassxc/issues/2447), [#4436](https://github.com/keepassxreboot/keepassxc/issues/4436), [#4743](https://github.com/keepassxreboot/keepassxc/issues/4743), [#4920](https://github.com/keepassxreboot/keepassxc/issues/4920), [#5719](https://github.com/keepassxreboot/keepassxc/issues/5719), [#5987](https://github.com/keepassxreboot/keepassxc/issues/5987).

### Inferences
- [I] Store the secret in a field with `ProtectedString(true, …)` (memory-protected); decode to `byte[]` only for the HMAC call and zero the array afterwards (`Array.Clear`/`MemUtil.ZeroByteArray`); never put the secret in `ToString()`, exception messages, trace/log output or crash dumps written by the plugin.
- [I] Copy codes via KeePass's own clipboard helper (KeePass API `ClipboardUtil` — name from developer knowledge, not verified in this research) so the user's auto-clear time and the history/cloud-exclusion formats above are applied consistently, instead of `System.Windows.Forms.Clipboard.SetText`.
- [I] Generated codes are low-value after ~30–90 s, but the **secret** is high-value: never copy the secret/otpauth URI to the clipboard by default; QR export should render in memory only (no temp PNG), shown on explicit user action, and closed on database lock.
- [I] Any timer-driven OTP window/column must subscribe to KeePass lock/close events and dispose itself; it must not count as "user activity" that resets the auto-lock timer (lesson from 8 KeePassXC issues above).
- [I] Placeholder: KeePass already owns `{TIMEOTP}`/`{HMACOTP}`; re-registering the same placeholder from a plugin risks conflict. Options: reuse KeePass's native `TimeOtp-*` fields (interop) or register a distinct placeholder. HOTP: increment and save counter atomically on each use, as KeePass does for `HmacOtp-Counter`.
- [I] Resolve the OTP at the moment of typing (after any `{DELAY}`), to avoid the KeePassXC stale-code bug.

### Gaps
- KeePass's default clipboard auto-clear time could not be verified from an official page (community claims of 12 s/20 s are unreliable). Check KeePass Options dialog/source.
- Version in which KeePass 2.x added native `{TIMEOTP}` was not found on the placeholders page.
- Whether KeePass's `ClipboardUtil` sets all three Microsoft formats (vs. only `ExcludeClipboardContentFromMonitorProcessing`) was not verified from source.

## 4. Security trade-off: TOTP secret in the same database as the password

### Takeaway
All four vendors offer integrated TOTP; their wording ranges from an explicit warning (KeePassXC) to "safe" with a caveat (1Password) to silence (Bitwarden's help page). The consistent factual core: against theft/decryption of the vault or compromise of the device, a co-located TOTP secret adds no protection; against password reuse, phishing-replay of a captured password, or server-side password leaks, it still helps.

### Cited Findings
- [V] KeePassXC user guide: "WARNING: Storing TOTP codes in the same database as the password will eliminate the advantages of two-factor authentication. If you desire maximum security, we recommend keeping TOTP codes in a separate database that you only unlock when needed." — [KeePassXC docs source](https://raw.githubusercontent.com/keepassxreboot/keepassxc/develop/docs/topics/DatabaseOperations.adoc) (published at [User Guide §Adding TOTP to an Entry](https://keepassxc.org/docs/KeePassXC_UserGuide.html#_adding_totp_to_an_entry))
- [S] KeePassXC maintainer (2017): "its more like 1.5FA … If an attacker has access to your main password database, they likely have access to your TOTP database as well. You likely store your backup codes in the main password database" — [#848](https://github.com/keepassxreboot/keepassxc/issues/848). Community consensus there: document it, avoid a scary in-app warning that deters TOTP use.
- [S] Maintainer on separate DB + auto-open: auto-open stores the second DB's key in the first, which "totally null and voids your additional security" — [#4491](https://github.com/keepassxreboot/keepassxc/issues/4491)
- [V] 1Password (Goldberg, 2015, "Second factor? No"): storing the TOTP secret with the password means no second-factor protection, but "you still have the benefits of the one-timeness of TOTP codes"; codes "are not reusable even if they are captured in transit" — [1Password blog](https://1password.com/blog/totp-for-1password-users)
- [V] 1Password (Barker, 22 Jun 2023): "storing your TOTP in 1Password is safe"; "you lack a true second factor when both secrets originate from the same device"; "there's no authenticator app or password manager on the market that can safeguard data on a compromised device"; "The correct choice is the one that works best for you." — [1Password blog](https://1password.com/blog/1password-2fa-passwords-codes-together)
- [V] Bitwarden's integrated-authenticator help page does not discuss the trade-off (feature requires Premium/paid org) — [Bitwarden](https://bitwarden.com/help/integrated-authenticator/)
- [V] Proton: "you should never use Proton Pass to secure your Proton Account using TOTP" (use a third-party authenticator); page does not discuss the general trade-off; 2FA is premium — [Proton support](https://proton.me/support/pass-2fa). Proton also ships a separate Proton Authenticator app ([BleepingComputer](https://www.bleepingcomputer.com/news/security/proton-fixes-authenticator-bug-leaking-totp-secrets-in-logs/)).

### Inferences
- [I] Honest wording proposal (short, non-alarmist, factual): "If this database is stolen and unlocked, the attacker gets both the password and the one-time codes for this account. Two-factor protection then only helps against attacks that don't involve this database (e.g. a leaked or phished password). For important accounts — especially the account protecting this database's storage/sync and your e-mail — consider keeping the OTP secret in a separate database with a different master key, or on another device." Show once (first setup) + in docs, with "don't show again"; no "best/most secure" claims.
- [I] Product options: (a) per-entry choice of target database ("store OTP in: this database / another open database"), (b) warn if the OTP database is auto-opened from the password database (per #4491 that defeats separation), (c) mark an entry as "contains OTP secret" in exports.

### Gaps
- No official Proton statement on the general same-vault trade-off was found; Bitwarden's broader docs (other pages/blog) were not searched.

## 5. What users complain about / request (KeePassXC TOTP issues, grouped)

Method: GitHub search API `repo:keepassxreboot/keepassxc TOTP in:title`, fetched 2026-10-23 → 248 results = **208 issues + 40 PRs**. ## 6. Input validation: Base32 with spaces/lowercase/padding, invalid lengths, very short secrets

### Takeaway
Real-world secrets arrive with spaces, lowercase, newlines, missing or extra `=`, or as a full `otpauth://` URI; strict decoders produced a long tail of bug reports. Normalise generously, but reject what cannot be valid Base32 and warn (not necessarily block) on secrets shorter than RFC 4226's 128-bit minimum.

### Cited Findings
- [V] Google Key URI: secret is Base32 (RFC 3548), padding "should be omitted" — [Key Uri Format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format); so URI-sourced secrets typically lack padding, while some services/tools add it.
- [V] RFC 4226: secret "MUST be at least 128 bits", 160 recommended — [RFC 4226 §4](https://www.rfc-editor.org/rfc/rfc4226); RFC 6238: key length SHOULD equal HMAC output (20/32/64 B) — [RFC 6238 §5.1](https://www.rfc-editor.org/rfc/rfc6238)
- [V] KeePass accepts four encodings: UTF-8 text, hex, Base32, Base64 (`TimeOtp-Secret`, `-Hex`, `-Base32`, `-Base64`, exactly one present) — [KeePass Placeholders](https://keepass.info/help/base/placeholders.html)
- [S] KeePassXC failures from strict parsing: spaces ([#1022](https://github.com/keepassxreboot/keepassxc/issues/1022)), spaces+lowercase ([#3754](https://github.com/keepassxreboot/keepassxc/issues/3754)), missing padding ([#3825](https://github.com/keepassxreboot/keepassxc/issues/3825), [#3874](https://github.com/keepassxreboot/keepassxc/issues/3874)), `====` ([#8300](https://github.com/keepassxreboot/keepassxc/issues/8300)), trailing `=` in exported QR breaking other apps ([#3255](https://github.com/keepassxreboot/keepassxc/issues/3255), [#12540](https://github.com/keepassxreboot/keepassxc/issues/12540)), newlines ([#6599](https://github.com/keepassxreboot/keepassxc/issues/6599), [#12024](https://github.com/keepassxreboot/keepassxc/issues/12024)), 58-char seeds ([#3988](https://github.com/keepassxreboot/keepassxc/issues/3988)), whole URI pasted as secret ([#9978](https://github.com/keepassxreboot/keepassxc/issues/9978)); invalid input silently not saved ([#3142](https://github.com/keepassxreboot/keepassxc/issues/3142)) or crashing ([#5105](https://github.com/keepassxreboot/keepassxc/issues/5105)).
- [S] otpauth label escaping bugs with `:` and `/` in entry titles ([#11731](https://github.com/keepassxreboot/keepassxc/issues/11731), [#2915](https://github.com/keepassxreboot/keepassxc/issues/2915)); spec forbids colons inside issuer/account — [Key Uri Format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format)
- [V, local computation] Normalising `"jbsw y3dp ehpk 3pxp"` → strip whitespace, uppercase, re-pad to a multiple of 8 → decodes to bytes `48 65 6c 6c 6f 21 de ad be ef` (the well-known `JBSWY3DPEHPK3PXP` test secret, 10 bytes = 80 bits, i.e. below the RFC 4226 128-bit minimum yet widely used in examples).

### Inferences
- [I] Normalisation rules (testable): trim; remove all whitespace (space, tab, CR, LF) and hyphens; uppercase; strip all trailing `=` then re-pad internally; if input starts with `otpauth://`, parse the URI (type, label, `secret`, `issuer`, `algorithm`, `digits`, `period`, `counter`) instead of rejecting.
- [I] Reject (with a specific message, keeping the dialog open and the user's input): characters outside `A–Z2–7` after normalisation; Base32 lengths that are impossible (remainder of length mod 8 equal to 1, 3 or 6); non-zero trailing bits (optional strict mode); empty secret; digits outside the supported range (KeePass native max 8; Bitwarden allows 1–10); period ≤ 0; unknown algorithm.
- [I] Warn but allow: decoded secret < 16 bytes (128 bits, RFC 4226 MUST is for servers that issue secrets — users cannot change a service's secret, so blocking would only break real accounts); SHA-256/512 key shorter than HMAC output.
- [I] Export: emit Base32 without padding in `otpauth://` URIs (Google spec) and percent-encode label parts; never write `=`.
- [I] Show a live preview code in the setup dialog so users can compare with the service before saving.

### Gaps
- RFC 4648 Base32 text was not fetched (behaviour of non-canonical trailing bits is from general knowledge). No survey of which services issue < 128-bit secrets.
